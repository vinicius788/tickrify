## 1. Objetivo

Tickrify é um SaaS de análise de gráficos de trading onde o usuário faz upload de uma screenshot de gráfico e recebe recomendações BUY/SELL/HOLD com análise técnica completa. A sessão focou em dois objetivos: (1) resolver erros críticos de produção (503 `worker_unavailable` e JSON truncado) e (2) preparar um plano de upgrade do prompt de IA do v4.0 para v5.0.

---

## 2. Contexto essencial

**Stack técnica:**
- **Backend:** NestJS + BullMQ (fila Redis) + Prisma (PostgreSQL via Supabase) + OpenAI GPT-4o/mini
- **Frontend:** React + Vite + TanStack Query + Clerk auth
- **Infra:** Render.com (plano Free) — dois serviços Docker: `tickrify-api` e `tickrify-worker`
- **Storage:** Supabase Storage para imagens
- **Pagamentos:** Stripe

**Arquitetura de processamento:**
1. API recebe imagem → faz upload para Supabase → adiciona job à fila BullMQ (Redis)
2. Worker BullMQ separado (`ai.worker.ts`) processa o job → chama OpenAI → salva resultado no DB
3. Frontend faz polling do status até `completed`

**Decisões já tomadas:**
- **Imagens anotadas:** Descartado — o JSON+card do frontend já é suficiente, não vale a complexidade
- **max_tokens:** Mantido em `3000` para quick analysis (2000 truncava o JSON; o campo correto já está em `ai.adapter.ts` linha ~418)
- **Polling do frontend:** Mudado de linear lento (`2000ms * attempts`, cap 10s) para rápido (`800ms base + 200ms/tentativa`, cap 3s)
- **Prompt v5.0:** Planejado com 4 gaps identificados — não implementado ainda, apenas documentado

## 4. Estado atual

**O que funciona em produção:**
- API sobe normalmente
- Autenticação (Clerk), pagamentos (Stripe), histórico de análises — tudo OK
- Endpoints: `/api/ticks/*`, `/api/ai/usage`, `/api/ai/analyses`

**O que está quebrado em produção:**
- `POST /api/ai/analyze` retorna `503 worker_unavailable` consistentemente
- Causa raiz identificada: `tickrify-worker` service no Render não está rodando ou crashando
  - `Dockerfile.worker` estava com bug (sem `apps/backend/node_modules`) — **corrigido localmente**
  - `RUN_EMBEDDED_WORKER=false` provavelmente definido no env group `tickrify-production` do Render — **precisa ser removido/alterado manualmente no dashboard**
- O `waitForQueueReady(5000)` espera 5s mas o worker genuinamente não está rodando — o timeout está funcionando como esperado, mas não resolve o problema subjacente

**O que está quebrado localmente:**
- Erro de IPv6: `Can't reach database server at 2600:1f13:838:6e32:...:5432`
- Causa: DNS local está resolvendo o Supabase pooler para IPv6, que a rede do dev não suporta
- **Não bloqueia nada no Render** (servidores Render têm IPv6)
- Fix local: Adicionar `?sslmode=require` ou forçar IPv4 explicitamente no `.env`

**Trecho chave adicionado em `ai.service.ts`** (método `waitForQueueReady`):
```typescript
private async waitForQueueReady(timeoutMs: number): Promise<import('./ai.queue').QueueReadiness> {
  const deadline = Date.now() + timeoutMs;
  const pollInterval = 500;

  let readiness = await getAiQueueReadiness();

  // Fast path: workers already up — return immediately with no delay.
  if (readiness.hasWorkers || !isProductionRuntime()) {
    return readiness;
  }

  // Slow path: poll until workers appear or timeout is reached.
  while (Date.now() < deadline) {
    await new Promise<void>((resolve) => setTimeout(resolve, pollInterval));
    readiness = await getAiQueueReadiness();
    if (readiness.hasWorkers) {
      this.logger.log(`[AiService] Worker became available after ${Date.now() - (deadline - timeoutMs)}ms`);
      return readiness;
    }
  }

  this.logger.warn(`[AiService] No workers detected after ${timeoutMs}ms — proceeding with last readiness state`);
  return readiness;
}
```
